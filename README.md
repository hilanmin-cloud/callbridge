# CallBridge

방한 외국인 관광객을 위한 **식당 예약 대행 서비스**의 프런트엔드입니다.

한국의 인기 식당 상당수는 온라인 예약 채널이 없고 전화로만 예약을 받습니다. 외국인 관광객은 언어 장벽 때문에 그 전화를 걸지 못하고, 한국 번호가 없어 식당의 확인 전화도 받을 수 없습니다. CallBridge는 이 연결을 대신합니다.

**배포 주소** → https://callbridge-kr.vercel.app

| 페이지 | 링크 |
|---|---|
| 랜딩 | https://callbridge-kr.vercel.app/ |
| 요청 접수 | https://callbridge-kr.vercel.app/intake.html |
| 결과 조회 | https://callbridge-kr.vercel.app/result.html |

> 접수 폼은 실제 데이터베이스와 연결되어 동작합니다. 연결 설정이 비어 있는 상태에서는 입력 내용이 어떤 구조로 저장되는지 미리보기로 확인할 수 있습니다.

## 화면 구성

| 파일 | 역할 |
|---|---|
| `index.html` | 랜딩 페이지 — 서비스 소개, 이용 방법, 요금, FAQ |
| `intake.html` | 요청 접수 폼 — 입력값 검증 후 데이터베이스 저장 |
| `result.html` | 결과 페이지 — 요청 번호로 예약 결과와 식당 이용 안내 조회 |

운영자용 화면은 고객 정보를 다루므로 이 저장소에 포함하지 않았습니다.

## 사용 기술

- **HTML5** — 시맨틱 요소, `<details>` 기반 FAQ, 스킵 링크, ARIA 속성
- **CSS** — Flexbox, 미디어 쿼리, CSS 변수, `clamp()` 반응형 타이포그래피, `IntersectionObserver` 기반 스크롤 연출
- **JavaScript (ES5)** — 의존성 없는 바닐라 구현, `fetch` API, `Intl.DateTimeFormat`
- **Supabase (PostgreSQL)** — REST API 기반 데이터 처리
- **GitHub + Vercel** — 커밋 시 자동 배포

빌드 도구나 프레임워크 없이 **정적 파일만으로 동작**합니다.

참고한 디자인: Linear(히어로 구성), Raycast(제품 시각화), Resend(기능 소개 그리드), Cal.com(예약 플로우)

## 리디자인 — 템플릿 느낌을 벗어나기

초기 버전은 레퍼런스 없이 만들어, 섹션마다 배경·정렬·여백이 모두 같은 전형적인 템플릿 구조였습니다. 기능과 정보 구조는 그대로 두고 시각 설계만 다시 했습니다.

### 구조부터, 색은 나중에

바로 코드를 고치지 않고 **와이어프레임으로 레이아웃을 먼저 확정**했습니다. 색과 글꼴이 들어가면 구조의 문제가 가려지기 때문입니다. 히어로 → 기능 소개 → 예약 플로우 순으로 섹션 단위로 끊어 검토한 뒤, 전체 흐름을 한 장에 모아 리듬을 확인하고 나서 구현에 들어갔습니다.

### 섹션마다 리듬을 다르게

기존 문제는 **스크롤해도 같은 화면이 반복되는 느낌**이었습니다. 원인은 모든 섹션이 흰 배경 · 좌측 정렬 · 동일 여백이었다는 점입니다.

| 섹션 | 배경 | 정렬 | 상단 여백 |
|---|---|---|---|
| 히어로 | 흰색 | 좌측 | 84px |
| 이용 방법 | 연회색 | 좌측 | 112px |
| 선택 이유 | 흰색 | **가운데** | **160px** |
| 요금 | 연회색 | 좌측 | 96px |
| FAQ | 흰색 | 좌측 | 88px |
| 마무리 | 진한 틸 | — | 72px |

배경은 번갈아 가고, 정렬은 한 번만 꺾습니다. 여백은 **머물게 할 곳을 넓게, 통과할 곳을 좁게** 두었습니다. 설득이 일어나는 구간에서 속도를 늦추고 마무리는 짧게 끝내는 구성입니다.

### 같은 내용도 형태를 다르게

이용 방법과 선택 이유가 똑같은 3분할 카드였습니다. 성격이 다른데 형태가 같으면 중복으로 읽힙니다.

- **이용 방법** — '순서'가 핵심이므로 선으로 이어진 가로 띠. 단계가 계단식으로 내려가 진행 방향을 보여줍니다.
- **선택 이유** — '병렬'이므로 카드. 큰 카드 2개와 작은 카드 2개를 지그재그로 배치하고, 큰 카드에만 시각 요소를 넣어 무게를 두었습니다.

### 문화권별 색 관습 반영

고객의 60% 이상이 일본·중화권입니다. 색의 의미가 한국·서구와 달라 조사 후 결정했습니다.

- 중화권에서 **빨강은 길함**이지만 한국·서구에서는 경고로 읽힙니다 → 사용하지 않음
- 중화권에서 **금색은 품격과 길함**, 서구에서도 성취의 의미 → 예약 확정 카드에만 사용
- **순백은 중화권에서 장례**와 연결됩니다 → 배경을 따뜻한 아이보리(`#FFFBF8`)로

언어별로 색을 바꾸는 방식도 검토했으나, 브랜드 일관성이 무너지고 관리 비용이 커져 **팔레트는 하나로 두고 가장 중요한 순간(예약 확정)에만** 문화 관습을 반영하는 방식을 택했습니다.

| 역할 | 색 | 사용처 |
|---|---|---|
| 기본 | `#0F5E5C` | 로고, 체크, 보조 버튼 |
| 포인트 | `#F0603F` | CTA, 강조 문구 |
| 확정 | `#C9962F` | 예약 확정 카드 |

### 다크 모드를 제거한 이유

초기에는 `prefers-color-scheme`로 다크 모드를 지원했으나 제거했습니다. 여행 예약 서비스(Klook, Trip.com, Agoda 등)는 공통적으로 밝은 화면만 제공합니다. 분위기가 중요한 서비스이고, 색 세트를 두 벌 관리하는 비용이 혼자 운영하는 환경에서 부담이 되기 때문입니다.

### 헤드라인 — 과장 대신 문제 해결

초안은 "전화로만 예약되는 가게야말로 갈 가치가 있다"였으나, **일본은 단정적인 광고 표현을 경계**하는 경향이 있어 폐기했습니다. 최종안은 고객이 실제로 겪는 두 가지 벽을 짚는 방식입니다.

> 말이 안 통해도, 그 식당 예약됩니다

주장 대신 사실을 말하고, "그 식당"이라는 표현으로 **이미 가고 싶은 곳이 정해진 사람**에게 말을 겁니다.

### 입력 폼 — 단계를 쪼개지 않고 덩어리로

단계형(Step 1-2-3) 구조를 검토했으나, 입력량이 한 화면에 들어갈 분량이라 '다음' 버튼을 누르는 수고만 늘어난다고 판단했습니다. 대신 한 화면 안에서 **어디에 / 언제·몇 명 / 누구 이름으로** 세 덩어리로 나누고 번호를 붙였습니다.

- 체크박스를 **칩(toggle)**으로 교체 — 선택 시 색 반전, 모바일 터치 영역 확보
- 인원은 숫자 입력 대신 **− / + 조절**
- 우측 요약이 **입력에 따라 실시간으로 채워지며 스크롤을 따라붙음**
- placeholder에 **구체적인 예시** 삽입 (`https://naver.me/xxxxx`, `Tanaka`)

### 애니메이션 — 스피너를 쓰지 않음

AI 통화 중 화면은 서비스의 핵심 순간입니다. 회전하는 스피너는 "처리 중"만 알릴 뿐 진행 상황을 전하지 못합니다.

- **동심원이 밖으로 번지는** 연출로 전파가 퍼지는 느낌을 표현
- 가운데 원이 **미세하게 커졌다 작아지며** 통화가 살아 있음을 표시
- 아래에 **진행 로그가 한 줄씩 누적**되어 현재 단계를 전달
- 완료 시 동심원이 멈추고 확정 카드가 떠오름
- "창을 닫아도 된다"는 안내로 대기 중 이탈 불안 해소

`prefers-reduced-motion`을 선언한 사용자에게는 모든 움직임이 멈추고 내용만 전환됩니다.

## 구현에서 다룬 문제

### 다국어 — 번역이 아니라 현지화

방한 관광객 통계상 일본·중화권 비중이 60%를 넘어, 기본 언어를 일본어로 두고 5개 언어(일본어·중국어 번체·간체·영어·한국어)를 지원합니다.

- 각 언어권의 문화에 맞는 표현 사용 — 좌석 형태를 일본어는 `カウンター・座敷・個室`, 중국어는 `吧台、和式、包廂`로 표기
- 날짜·시간은 `Intl.DateTimeFormat`으로 현지 형식을 따르되 **시간대는 한국 시간으로 고정** — 고객 기기가 자국 시간대일 때 예약 시각이 어긋나는 문제 방지
- 결과 페이지에서 안내문은 고객 언어, **식당에 보여줄 문장은 한국어**로 분리 — 읽는 주체가 다르기 때문
- 첫 방문 시 `navigator.language`로 브라우저 언어를 감지해 자동 적용, 이후 선택은 `localStorage`에 저장

### 입력 설계 — 되묻지 않아도 되는 폼

초기에는 희망 일시를 하나만 받았으나, 그 시간이 불가능할 경우 고객에게 다시 확인해야 해 처리가 지연되는 구조였습니다. 우선순위를 둔 복수 입력과 수용 가능 조건을 함께 받도록 재설계해, 추가 확인 없이 처리할 수 있는 범위를 넓혔습니다.

### 반응형 — 폴더블 대응

폴더블 기기의 접힌 상태(약 380px 폭)에서 날짜·시간 입력 요소가 컨테이너를 벗어나는 문제를 확인하고, `flex-wrap`과 미디어 쿼리로 세로 배치되도록 수정했습니다. 좁은 화면에서는 좌우 여백과 카드 패딩도 함께 줄여 가용 폭을 확보했습니다.

iOS에서 입력 요소의 글꼴이 16px 미만이면 포커스 시 화면이 자동 확대되는 문제가 있어, 모든 입력 필드를 16px 이상으로 유지했습니다.

### 접근성

- 체크박스 라벨 영역 전체를 클릭 가능하도록 `<label for>` 연결, `user-select` 해제로 드래그 시 텍스트 선택 방지
- 터치 대상 최소 높이 44px 확보
- 스킵 링크, `aria-labelledby`, `aria-pressed` 적용
- `input type`을 용도에 맞게 지정해 모바일에서 적절한 키보드 노출

### SEO

- 페이지별 title·description, canonical, Open Graph
- `hreflang` 5개 언어 + `x-default`
- JSON-LD 구조화 데이터 — `Service`, `FAQPage`, `HowTo`
- `robots.txt`와 `sitemap.xml`, 고객 정보가 담기는 결과 페이지는 `noindex`로 색인 제외

## 데이터 구조

```
customers ─┐
           ├─ requests ─┬─ request_slots   (순위별 희망 일시)
venues ────┘            ├─ calls           (통화 기록)
                        └─ results         (결과)
```

요청 하나를 중심으로 관련 정보를 분리했습니다. 희망 일시는 개수가 가변적이므로 별도 테이블로 두고, 결과는 요청당 하나만 존재하도록 설계했습니다.

업체 데이터는 공공데이터포털의 지방행정 인허가 정보를 가공해 적재했습니다. CSV 인코딩(CP949/UTF-8)을 자동 판별하고, 폐업 업소와 전화번호 누락 건을 제외한 뒤 중복을 정리하는 적재 도구를 별도로 만들었습니다.

## 직접 해결한 문제들

작업하면서 마주친 문제와 해결 과정입니다.

### 긍정으로 오인하던 응답 처리

"네, 잠시만요"처럼 문장이 긍정어로 시작하지만 실제로는 확인을 요청하는 응답이 있습니다. 초기 구현은 앞부분만 보고 수락으로 처리했는데, 실제 상황에서 가장 흔한 패턴이라 잘못된 결과가 나올 수 있었습니다. 문장 전체의 맥락을 보고 대기 상태와 수락을 구분하도록 수정했습니다.

### 되묻는 질문을 넘어가던 문제

상대가 조건을 확인하기 위해 되묻는 경우, 앞부분의 긍정 표현만 보고 다음 단계로 넘어가는 문제가 있었습니다. 되묻기를 먼저 판별해 답변이 필요한 경우와 그렇지 않은 경우를 분기하도록 처리 순서를 바꾸었습니다.

### 중복 데이터가 쌓이던 문제

접수 시 입력된 업체명으로 레코드를 매번 새로 생성해, 테스트를 반복할수록 정보가 비어 있는 중복 행이 누적됐습니다. 기존 레코드를 먼저 조회해 있으면 연결하고 없으면 요청에 이름만 저장하도록 변경한 뒤, 이미 쌓인 데이터는 참조 관계를 해제하고 정리했습니다.

### UUID 부분 검색 오류

결과 조회에 요청 번호 앞 여덟 자리를 사용했는데, UUID 타입에 문자열 패턴 매칭을 시도해 데이터베이스 오류가 발생했습니다. 전체 UUID인 경우와 일부만 입력된 경우를 나누어 처리하도록 수정했습니다. 다만 현재 방식은 조회 범위에 제한이 있어, 별도의 조회 코드를 발급하는 구조로 개선할 예정입니다.

### 입력 식별 정확도

업체명만으로는 같은 이름의 다른 지점과 구분되지 않는 문제가 있었습니다. 지도 링크를 우선 입력 항목으로 올리고 공유 방법을 안내해, 사용자가 특정 지점을 정확히 지정할 수 있도록 했습니다.

## 앞으로 보완할 부분

- **인증** — 현재 데이터베이스 접근 정책이 개발 편의를 위해 열려 있습니다. 공개 운영 전 소셜 로그인을 도입하고 본인 요청만 조회 가능하도록 제한해야 합니다.
- **조회 코드 분리** — 요청 번호 일부로 조회하는 현재 방식 대신 별도의 조회 코드를 발급하는 구조가 안전합니다.
- **결과 알림** — 현재는 운영자가 링크를 전달합니다. 푸시 알림으로 대체할 예정입니다.
